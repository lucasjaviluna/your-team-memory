El sistema

¿Qué es team-memory?

El conocimiento generado en sesiones de IA se pierde cuando se cierra la terminal. team-memory lo captura, lo estructura y lo hace disponible para cualquier miembro del equipo en cualquier sesión futura — no solo devs, también QA, diseñadores, POs y analistas funcionales.

🔐 Auth por roles

reader / writer / admin. Token personal por dispositivo. Invite tokens de un solo uso. Completamente transparente para el usuario final.

🌐 Un comando

Registra el MCP en Claude Code, Copilot, VS Code, Cursor y OpenCode. El token queda configurado automáticamente en cada herramienta.

🖥️ TUI completa

7 pantallas: Dashboard, Entradas, Búsqueda, Detalle, Compactar, Admin (roles), Selector de proyecto.

Transporte

Modos de conexión

💻 stdio — servidor local

El MCP corre como subproceso del cliente IA. Sin red, sin puertos. Solo para admins del servidor.

MCP_TRANSPORT=stdio
# ⚠ Expone credenciales al cliente

🌐 Streamable HTTP — producción

Servidor compartido del equipo. Endpoint /mcp, modo stateless. Auth via Bearer token.

MCP_TRANSPORT=http
MCP_PORT=3100
AUTH_ENABLED=true
V4.5

Sistema de autenticación

Auth por Bearer token, transparente para el usuario final. El instalador configura el token automáticamente en cada herramienta de IA. El agente no necesita hacer nada especial — el token se incluye en cada request sin intervención.

Tres tablas en la DB

-- users: quién puede acceder al sistema
users (id UUID, username TEXT UNIQUE, email TEXT, role TEXT, created_at, revoked_at)

-- api_tokens: un token por dispositivo por usuario
api_tokens (id UUID, token TEXT UNIQUE, user_id UUID→users, device_name TEXT,
            created_at, last_used, revoked_at)

-- invite_tokens: de un solo uso, expiran en 48hs
invite_tokens (id UUID, token TEXT UNIQUE, role TEXT, created_by UUID→users,
               used_by UUID→users, expires_at, used_at)
ℹ️
AUTH_ENABLED=false en el .env desactiva la auth completamente sin cambios de código. Útil para desarrollo local o migración gradual.

Flujos de instalación

Onboarding transparente

Bootstrap — primer admin (una sola vez)

# 1. Configurar en .env
AUTH_ENABLED=true
ADMIN_BOOTSTRAP_TOKEN=token-secreto-temporal

# 2. Aplicar migración
npm run db:migrate:003

# 3. Crear el primer admin
curl -X POST http://IP:3100/auth/bootstrap \
  -H "Authorization: Bearer token-secreto-temporal" \
  -H "Content-Type: application/json" \
  -d '{"username": "lucas", "device_name": "MacBook Lucas"}'
# → guarda el token que devuelve — es tu API key
⚠️
El bootstrap solo funciona una vez — cuando no existe ningún usuario. Después de crear el primer admin, el ADMIN_BOOTSTRAP_TOKEN queda invalidado.

Usuario nuevo — primer dispositivo

# Admin genera invite (TUI → Admin → Crear invite, o endpoint)
curl -X POST http://IP:3100/auth/invites \
  -H "Authorization: Bearer sk-admin-..." \
  -H "Content-Type: application/json" \
  -d '{"role": "writer"}'
# → { "token": "inv-abc123...", "usage": "npx ... install --invite inv-abc123" }

# Admin comparte el invite por Slack/email
# Usuario instala:
npx github:tu-org/team-memory install --invite inv-abc123

# El instalador pide username y device_name, muestra el token una sola vez:

Dispositivo extra o token perdido

# Tiene el token anterior — dispositivo extra
npx github:tu-org/team-memory install --token sk-writer-abc123

# Perdió el token — admin genera uno nuevo
curl -X POST http://IP:3100/auth/users/:id/token \
  -H "Authorization: Bearer sk-admin-..."
# → nuevo token para ese usuario, mismo rol
Auth REST

Endpoints de autenticación

Todos en el mismo puerto que el MCP (http://IP:3100). El endpoint /mcp requiere Bearer token cuando AUTH_ENABLED=true.

EndpointAuth requeridaDescripción
POST /auth/bootstrapBootstrap tokenCrea el primer admin (un solo uso)
POST /auth/registerInvite tokenRegistro de usuario nuevo
GET /auth/meBearerVerificar token y obtener info del usuario
POST /auth/tokens/deviceBearerNuevo token para otro dispositivo
POST /auth/invitesAdminCrear invite token (expira en 48hs)
GET /auth/invitesAdminListar invites activos
GET /auth/usersAdminListar usuarios con tokens activos
POST /auth/users/:id/tokenAdminGenerar token para usuario existente
PATCH /auth/users/:id/roleAdminCambiar rol del usuario
DELETE /auth/tokens/:idAdminRevocar un token específico
DELETE /auth/users/:idAdminRevocar usuario + todos sus tokens

Calidad

Deduplicación automática en save_memory

Paso A — Exact title match

Normaliza (lowercase, trim). Score 1.0. Sin costo de embedding. Solo dentro del mismo project + area + type.

Paso B — Near-duplicate RRF ≥ 0.030

Genera embedding, corre vectorial + FTS, combina con RRF. Umbral conservador. Mismo scope.

// Respuesta cuando hay duplicado
{ "saved": false, "duplicate_detected": true,
  "duplicate": { "id": "uuid", "title": "...", "content_preview": "...", "score": 1.0 },
  "suggestion": "Use update_memory with entry_id..." }

// El agente evalúa y decide:
// score 1.0 → update_memory casi siempre
// score ~0.030 → evaluar content_preview
// force: true → insertar igual

Protocolo del agente

Flujo durante una sesión

1

Resolver project_slug

Buscar .team-memory.json subiendo hasta .git. Si no existe → flujo interactivo.

2

Bootstrap — get_context

Antes de la primera respuesta sustancial. SUMMARY y TASK_CONTEXT llegan primero.

3

Buscar antes de responder

search_memory antes de preguntas técnicas. Si hay ANTI_PATTERN relevante, advertir proactivamente.

4

Resolver area

Cascada: area_map → default_area → heurística → preguntar. Informar la fuente.

5

save_memory → manejar duplicate

Si duplicate_detected: true → evaluar y decidir entre update o force.

6

Error 403

Informar que la operación requiere un rol superior. No reintentar.

7

Consolidar al cerrar

SUMMARY si la sesión fue significativa. TASK_CONTEXT para lo pendiente.

⚠️
compact_memory y delete_memory solo a pedido explícito. Nunca de forma autónoma. Siempre con dry_run primero para compact.
